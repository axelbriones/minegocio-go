# Detalle de Implementación: Tarea 8 - Sync Engine (Offline-First)

## Resumen de lo Realizado
En esta tarea se sentaron las bases del motor de sincronización (Sync Engine) para la aplicación móvil "MI NEGOCIO GO", garantizando un funcionamiento robusto bajo una arquitectura **Offline-First**.

### Detalles Técnicos
1.  **Modificación del Esquema SQLite (`mobile/src/database/index.ts`)**:
    *   Se agregaron columnas clave para el control de versiones y resolución de conflictos a las tablas de entidades principales (`products`, `sales`, `purchases`):
        *   `updatedAt`: Timestamp de la última modificación.
        *   `version`: Entero incremental para identificar la versión del registro.
        *   `isDeleted`: Bandera lógica (soft-delete) para sincronizar eliminaciones.
    *   Se creó una nueva tabla especializada llamada `sync_queue` para almacenar la cola de operaciones (CREATE, UPDATE, DELETE) pendientes de enviar al backend. Esta tabla guarda la entidad, el ID, el payload, el estado (`PENDING`, `ERROR`) y la cantidad de reintentos (`retryCount`).

2.  **Lógica del Motor de Sincronización (`mobile/src/sync/index.ts`)**:
    *   **Queue (Encolamiento)**: Se implementó la función `addToSyncQueue` que intercepta las operaciones CRUD locales y las guarda en la base de datos `sync_queue` de forma persistente.
    *   **Retry Mechanism (Reintentos)**: El proceso de sincronización (`processSyncQueue`) extrae elementos pendientes e intenta empujarlos al servidor (simulado con `pushToBackend`). Si falla (por ejemplo, por falta de red), incrementa el contador de reintentos en SQLite mediante `markSyncItemError`. Tras alcanzar un máximo (ej. 3 reintentos), detiene la ejecución para no saturar el dispositivo.
    *   **Conflicts & Versionado (Resolución de Conflictos)**: Se implementó la función `resolveConflict` que, ante un mismo registro editado local y remotamente, decide quién gana basándose principalmente en el número de `version`. Si los números de versión son iguales, se desempata usando el timestamp de `updatedAt` (la edición más reciente gana).
    *   **Merge (Fusión de Datos)**: Se creó `mergeRemoteItem` para integrar correctamente un objeto recibido del servidor a la base de datos local de SQLite. Inserta el registro si no existe localmente, o aplica las reglas de resolución de conflictos para actualizar de manera segura la fila existente si es necesario.

## ¿Qué falta por hacer? (Próximos Pasos)
1.  **Integración en el App Lifecycle**: Actualizar los hooks o servicios que realizan el CRUD de la aplicación móvil para que efectivamente llamen a `addToSyncQueue` cuando crean/editan una venta o producto.
2.  **Conexión Real al Backend**: Cambiar la función de prueba `pushToBackend` (que actualmente simula latencia y errores de red aleatorios) por una llamada `fetch` o `axios` real a la API de NestJS del backend.
3.  **Manejo de Conectividad (NetInfo)**: Incorporar un detector de conexión a internet (como `@react-native-community/netinfo`) para disparar `processSyncQueue` automáticamente cada vez que el celular pase de estar "Offline" a "Online".
4.  **Sincronización en Background**: Evaluar e implementar tareas en segundo plano (usando por ejemplo `expo-background-fetch` o `expo-task-manager`) para que la sincronización pueda ocurrir aunque el usuario no tenga la app abierta, garantizando datos siempre frescos.
